# Repository Guidelines

## Project Structure

`src/` composes and starts Cordis; keep business logic out of it. Put leaf behavior in `plugins/`, replaceable contracts and implementations in `packages/seam/` and `packages/impl/`, cross-cutting policy in `packages/policy/`, shared feature sets in `packages/bundle/`, and browser pages in `packages/client-ui/`. `profiles/` adjusts runtime bundles. `composed.cordis.yml` is generated by `src/compose.ts`; edit source manifests instead. Production UI assets are built before release and checked at startup; development startup builds them automatically. Production systemd makes the checkout read-only except for that generated manifest and `data/`. `docs/`, `dev-cordis/`, and `.rules/` hold architecture and project decisions. Runtime databases, logs, uploads, and workspaces belong under `data/` and must not be committed.

## Build, Test, and Development

Use Node.js 22.5.0 or newer; npm enforces this through `engines` and `.npmrc`. Run commands from this directory:

- `npm ci` installs the exact lockfile on a clean checkout or CI runner; use `npm install` after dependency or workspace changes and commit the updated lockfile.
- `npm run migrate` applies SQLite migrations; back up local data before destructive maintenance.
- `npm run dev` starts the development process; `npm start` starts the service; `npm run stop` stops it.
- `npm run typecheck` checks TypeScript. `npm run gate:static` runs local checks without a live service.
- Start the service, then run `npm run gate:runtime` for HTTP, UI, smoke, and runtime verification. `npm run gate` runs both gates.

## Code and Test Conventions

Read `.rules/IRON-RULES.md` and the relevant architecture notes before changing code. Preserve the L0–L12 dependency direction and package boundaries; run `npm run lint:deps` when changing dependencies. TypeScript uses ES modules. Follow neighboring naming and formatting, and use the shared UI components and design tokens instead of page-local styling. Add focused, failure-sensitive verification for behavior changes. Gate and migration results must be recorded in `action_log` as required by the project rules.

## Identity and Product Boundaries

Admin accounts are separate from Team accounts. Admin pages manage system configuration, accounts, and logs; Team members use shared Teamspace workspaces, knowledge, and the shared Agent catalog. Do not add Admin bridges to Team navigation or per-user ownership of shared Agents. See the parent workspace's `../story1.md`, `../story2.md`, `../TODO.md`, and `../Problem.md` for approved product direction; document unfinished behavior rather than implying it is implemented.

## Commits and Pull Requests

Recent commits use concise prefixes such as `功能:` and `修复:`. Keep changes focused. A pull request should describe behavior and architecture changes, list checks run, link related work when available, and include screenshots for UI changes.

## Configuration and Security

Keep ports, credentials, and machine-specific values in `.env`; update `.env.example` for new settings. Set `SETTINGS_ENCRYPTION_KEY` to a securely generated 32-byte key so API credentials are encrypted at rest; back it up separately from SQLite data. Never commit `.env`, secrets, generated bundles, local databases, caches, or temporary files. Production setup is documented in `docs/DEPLOYMENT.md`.
