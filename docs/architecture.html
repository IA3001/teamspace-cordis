teamspace-cordis · 最小框架架构图

两张图说明这套骨架：框架怎么被点着，以及点着之后内部怎么组织。

一、启动链路

从你敲下 npm start 到插件就位，一共四步。左侧与右侧的两个虚线框是外部输入，它们不是代码，是磁盘上的配置文件。

图 1 · 启动链路

两处值得注意的设计。 .env 用一条虚线同时到达 run.sh 与 cordis.yml，所以端口只在一处定义、一处修改； cordis.yml 之所以能读到它，是靠 !!js 标签直接求值 process.env，而进程环境变量由 run.sh 用 Node 官方的 --env-file 载入。 整条链的终点是插件清单——加功能就是在那里加一行。

二、运行时结构

框架点着之后，src/index.ts 的任务就结束了。此后所有能力都来自挂在 Context 上的插件——虚线大框就是 Context。

图 2 · 运行时结构

高亮的 plugin-server 是唯一「提供服务给别人用」的插件——它把 ctx.server 注册到 Context 上， 其余插件通过 inject 声明依赖来使用它。斜体虚线箭头 inject: server 是整张图最值得理解的一处机制。

三、从图里能读出的三条结论

① 内核极薄，功能全在插件里

src/index.ts 只有 30 行、零业务代码，它干的事就是「建 Context、挂 Loader、让 include 去读清单」。所有能力——HTTP 服务、健康检查、以后的日志系统——都是插件。在 cordis.yml 里删掉一项，那个功能连同它注册的路由、事件、定时器会被框架自动回滚。

② inject 是插件之间唯一的耦合方式

plugins/health 声明 inject = ['server']，语义是：

  • server 服务没就绪 → health 不加载
  • server 被重载 → health 自动回滚并跟随重载
  • 加载顺序由依赖决定，与清单里的书写位置无关

所以插件之间不需要互相 import，也不需要谁去「启动」谁。plugins/app 没有任何依赖，框架就并发地把它挂上去。

③ 端口一致性是「结构保证」的，不是靠人记住

图 1 里 .env 那条虚线同时到达 run.sh（载入并校验）与 cordis.yml（!!js 读进程环境变量），两条路都来自同一个文件。图 2 里 server 的副标题写的是「监听 .env 里的 8080」——8080 这个数字没有散落在三处，它只有一处，其余全是引用。

一句话总结这套骨架的规矩

src/ 只放启动代码，plugins/ 放所有功能，cordis.yml 决定谁上谁下，.env 决定跑在哪。四条边界互不越界，所以加功能时你只需要动两个地方——新建一个插件文件，然后在清单里加一行。
