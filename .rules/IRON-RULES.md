## 铁律 1　web 端 UI 禁止手写 / 自制样式

**原话（用户指示，2026-09-27）**：

> 关于 web 端的 ui ，我有铁律：禁止手写/自制 样式，
> 也就是说，必须有一套统一的，快捷的（也许可以预定义/或者使用已有的 ui 轮子库，比如蚂蚁的 ui）
> 反正就是，样式的封装越简洁越好（就像面向对象先定义好类和属性封装好，然后用的时候直接 new 一样，
> 而不是用的时候直接现写，导致屎山代码，），这也是为了我的系统主题风格一致

### 约束地位：这是**根本前提**，不是建议

用户原话：

> 以上的内容必须是根本的前提，如果上方的内容无法做的完美，不符合我的预期，就禁止下面的事情进行

也就是说：**这条做不到位，web 界面相关的工作就不许开工。** 不存在「先写出来再慢慢重构样式」。

### 为什么是铁律

样式一旦允许「用的时候现写」，每个页面都会各自发明一套间距、颜色、圆角。
三个月后的结果不是「样式有点乱」，而是：

- 改一次主题要翻遍所有页面，没人敢改 → 与「系统主题风格一致」这个**目标本身**直接冲突
- 新页面靠复制旧页面的样式开始，错误随之复制 → 页面越多，回圈越贵
- 说不清「这个圆角为什么是 6px」→ 无法判断哪些是设计意图、哪些是随手写的

用户的类比很准确：**组件库 = 类，props = 构造参数，设计令牌 = 属性定义。**
用的时候只负责「new」，不负责重新定义类。

### 落地动作（每条都可检查）

1. **先定组件库，再写界面。** 选型未定之前，**不许开始写任何界面代码**。
   定了就写死在本文档的「选型」表里，不许在两个页面上用两套。
2. **样式的来源只有三个，不允许第四个**：
   - 组件库组件的 props（`size` / `type` / `variant` / `status` 之类）
   - 组件库的布局原语（`Row` / `Col` / `Space` / `Flex` 之类）
   - 项目设计令牌（语义化的颜色 / 间距 / 圆角 / 字号）
3. **业务代码里禁止出现**：
   - 内联样式：`style={{ ... }}`、`style="..."`
   - 自写样式块：`<style>`、独立 `.css` / `.scss` 文件
   - 硬编码视觉值：`#RRGGBB`、`rgb()`、`hsl()`、以及裸的 `px` 间距与圆角
4. **封装成「类」，而不是在页面里现写。**
   同一视觉语义出现第二次，就必须抽成组件或令牌；
   页面只做**组合**，不做**定义**。
5. **主题一致性靠令牌。** 亮 / 暗两套值只在令牌里定义一次，
   业务代码只引用语义名（如 `--color-bg-surface`），不引用具体色值。
6. **要有会红的门禁断言。**
   扫描 web 业务源码，出现内联样式 / 自写样式块 / 硬编码颜色 → 判红。
   断言必须**故意改坏一次确认它真的会红**（空断言与源码文本匹配一律不接受）。
   落地实现：`scripts/lint-styles.sh`，跑 `npm run lint:styles`。
   它扫 `src/`、`plugins/`、`packages/`、`web/`（`docs/`、`node_modules/` 不扫，与本文件「适用范围」一致）。
   已实测的三种改坏方式见脚本末尾「自检记录」。

### 判红条件

- web 业务代码里出现内联样式，或自写的样式块 / 样式文件
- 出现硬编码的颜色、间距、圆角、字号
- 组件库已有现成能力，却自己造一个
- 同一视觉语义在不同页面用了不同实现
- 门禁里没有对应的「样式来源」断言

### 选型（定后写死在这里，不许漂移）

**定于 2026-09-27，依据用户选择「用官方 webui 栈，我们零 UI 代码」。**

**为什么不用第二套组件库（比如蚂蚁的 ui）**：外壳已经把 element-plus 的 `--el-*`
全部映射到设计令牌，同一页面再引一套组件库，必然出现「两套令牌、两套圆角、两套间距」——
正是铁律 1 要消灭的东西。**想换组件库 = 换外壳，不是加一套。**

**选型扩展后追加的判红条件**：

- 代码里出现 `--k-*` / `--bg0`–`--bg3` / `--fg0`–`--fg3` / `--el-*` → 判红（用错令牌层）
- 出现外壳 `app/styles` 之外的第二个令牌来源 → 判红
- 在页面 / client-ui 包里 `import 'element-plus'`（外壳已全局注册，再引一份就是两套） → 判红

## 铁律 2　开发过程必须让人类「看得见」，不许自己闷头搞

**原话（用户指示，2026-09-27）**：

> 你要注意，还有一个铁律：你开发的时候，必须可以让我可以通过控制台 / web ui 等方式，
> 让我直到你干了什么，效果怎么样，不要一味的自己搞

### 约束地位

与铁律 1 **同级**：不可协商。整个开发过程都受它约束，不只是交付物。

### 两个要求，别混成一个

1. **可见** —— 「我干了什么、效果怎么样」必须能在**控制台 / web UI** 看到，**不能只在聊天里说**。
2. **不闷头搞** —— 不许长时间自主连续推进；到阶段 / 里程碑要**交回控制权**。

### 为什么是铁律

- **看不见 = 人类失去控制权。** 只能事后翻代码猜，等于把判断力押在 AI 的自我汇报上。
- **本项目要吃自己的狗粮。** 这仓库要造的正是「多人 + 多 Agent 协作的可观察系统」，
  它自己的开发过程却看不见 —— 那是自相矛盾。
- **与用户既有偏好一致。** 「明确 @指令控制流程」「AI 不要一次输出过多」「不要擅自连续推进」
  已经写在别处；这条是把它从**自觉**升级成**设施要求**。

### 落地动作（每条都可检查）

1. **观测点先于结论。** 任何汇报都必须带「去哪看」：端口 + 页面 + 具体位置（表名 / 日志关键字）。
   **只在对话里说、控制台查不到的结论，等于没说。**
2. **开发动作要留痕。** 门禁（`npm run lint:*`）、`typecheck`、`migrate`、`seed` 每次执行都要写一条记录落库，
   在 5172 的**数据库页 / 日志页**可查。**跑过却不留痕 = 违规。**
3. **调试控制台是常驻开发设施，不是 M1 的一次性交付。** 改任何东西都不许把 5172 弄丢；
   它必须随时能回答三件事：**现在有哪些插件 / 最近发生了什么 / 数据长什么样**。
4. **阶段状态有唯一出处且可见。** P0~P5 的进度与验收结果要能从控制台看到，不许只躺在文档里。
5. **长任务分段交还控制权。** 干完一个阶段或一个大动作，先汇报 + 请示，不连续推进。
6. **要有会红的门禁断言**（见「判红条件」末条，落点在 `dev-cordis/MODULE-PLAN.md` 第 6 节 ⑨ ⑩）。
7. **可见性页面同样受铁律 1 约束** —— 不许为了「让过程可见」而手写 / 自制样式。

### 判红条件

- 汇报里的结论**在控制台 / 日志里查不到**
- 跑过门禁 / 迁移，却没留下可查的记录
- 调试控制台（5172）被弄坏，或不再反映真实状态
- 阶段状态只存在于文档或对话里，控制台看不到
- 没有对应的「可见性」断言

### 诚实记账：现在做到哪了

| 项 | 现状 |
|---|---|
| 5172 三页（插件 / 日志 / 数据库）真实数据 | ✅ M1 已跑通 |
| 控制台可达性**脚本**断言 | ✅ **已建（2026-09-27，P0）** —— 断言 ⑩，`scripts/check-console.sh`（`npm run check:console`）：外壳 + 三页共 7 个 URL 全 200 才通过；**故意改错 `DEBUG_PORT` → 退出码 1** 已实测 |
| 「动作写库」留痕 | ⬜ **未做** —— 断言 ⑨（待 P1 有库有表） |
| 阶段状态可见 | ⬜ **未做** |

> ⚠ 也就是说：**铁律 2 目前只完成了一半**（能看运行时状态、也有了可达性门禁，但**还看不到「我干了什么」**）。
> 这个缺口本身必须显式记在账上，不许当成已完成 —— 否则就是本铁律最讽刺的违反方式。

## 铁律 4　机器人可插拔入驻，开会功能不回退

**原话（用户指示，2026-09-29）**：

> 也就是说，这个插件系统必须承受的住新 机器人 的加入，除了支持基本的会议中的机器人，
> 还要支持新的机器人比如开发项目者、测试者等，他们有自己的生命，有自己的工作区，有自己的天地，
> 可以理解为一个 Coding Agent，因此这个插件系统必须经得起**通过添加插件的方式添加入驻**这种
> Coding Agent，同时又不失之前定义好的开会功能，支持机器人的特殊功能，比如开发项目之类的

### 两条不变式（缺一即违规）

1. **入驻 = 纯新增。** 新增（或停用）一个机器人——会议机器人或 Coding Agent——只允许
   「**新增一个包 + patch 层加一行**」，任何既有文件零改动。
2. **开会功能不回退。** 机器人怎么加，`npm run gate` 十一门禁都必须保持全绿；
   `verify:staging` / `verify:orchestrator`（开会链路）回归不许红。

### 为什么是铁律

- 「插件系统」的名分靠这条撑着：加一个 agent 要改核心代码，那它就不是插件，是改装。
- Coding Agent 的「自己的生命 / 自己的天地 / 自己的工作区」都有既有机制承接，**不许为某个 agent 开后门**：
  生命 = 插件生命周期 + 每 agent runtime；天地 = cordis isolate realm（5172/5174 隔离先例）；
  工作区 = `space-workdir` 缝（每 agent 文件工作区）。
- 开会功能是既有承诺；入驻机制再花哨，把会开崩就是回退。

### 落地动作（每条都可检查）

1. **入驻只有一条路：向 `space-agent` 缝注册**（`AgentDescriptor`），不是往核心或会议链路里加特判。
2. **要有会红的门禁断言**（MODULE-PLAN 第 6 节断言 ⑪，P6 建）：
   入驻白名单校验（git 路径：新增/停用 agent 时除「新增包 + patch 层行」外不得有既有文件改动）+ 开会回归。
3. **每个新 agent 入驻必须实测「改坏会红」**（故意把 agent 特判写进核心文件 → 判红；还原 → 复绿）。
4. **特殊能力走既有缝**：开发 / 测试等能力 = `space-tool` 工具缝 + 沙箱 policy，不得绕开。

### 判红条件

- 新增 / 停用一个机器人需要改动任何既有文件（「新增包 + patch 层一行」之外）
- 把某个 agent 的特判写进核心代码或会议链路
- 加了机器人之后，开会功能门禁（verify:staging / verify:orchestrator / gate 全链）红
- 门禁里没有对应的「可插拔入驻」断言
