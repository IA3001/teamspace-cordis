# 人与多 Agent 协作产品：竞品调研与产品方向

日期：2026-10-15。对象：`teamspace-cordis` 的**产品本身**，与 DSH Agent-Native 开发流程调研分开。

## 结论

当前的问题不是少一种颜色或几个按钮，而是用户仍需亲自把会话、Agent、待办、执行、文件和验证串起来。已有技术能力没有形成稳定的产品使用路径。最近的局部布局修复有价值，但不能代替产品结构设计。

建议第一阶段定位为：**小团队与多个 Agent 在同一协作空间里讨论、分工、执行并验收交付物。**先用研发小任务验证，再考虑推广到文档、研究等工作。这是根据现有使用诉求提出的方向，不是已经确认的新产品定位。

主参考 Taskade 的协作组织、Linear 的任务与责任模型；以 Dify 学习配置和运行反馈，以 OpenHands 学习代码交付。Teams 与 LangSmith 分别补充会议成果、执行追踪设计。不能把六种产品的页面直接拼在一起。

本轮交付：[证据与边界](sources.md)、[长期产品结构建议](direction.md)。当天实施范围已收敛为[现有页面的共享文字导航](../../product/README.md)，不要求一次完成全量产品改造。

## 六个参考对象

| 产品 | 与本项目的关系 | 核心产品对象 | 最值得学什么 | 不应直接照搬什么 |
| --- | --- | --- | --- | --- |
| Taskade | 最接近的直接参考 | 工作空间、项目、任务、Agent 团队 | 工作有容器；Agent 在任务上下文中协作 | 全套应用生成器、所有视图和自动化能力 |
| Linear | 任务协作与视觉结构参考 | Issue、负责人、委托 Agent、项目 | 人的责任与 Agent 执行分开，活动归属于具体任务 | 大型研发组织的全部层级和流程 |
| Microsoft Teams Facilitator | 多人会议场景参考 | 会议、笔记、议程、会后成果 | 讨论之后有持续可访问的结果入口 | Microsoft 365 的复杂权限、许可和生态依赖 |
| Dify | 配置与运行管理参考，非多人群聊替代品 | 应用、模型供应商、知识、运行日志 | 配置有归属，运行有独立详情和反馈 | 把工作流画布强行作为所有用户的首页 |
| OpenHands / Agent Canvas | 编码执行与交付参考 | 会话、工作区、执行后端、模型 | 代码任务在实际文件与执行环境中完成 | 将我们的通用协作界面直接改成开发 IDE |
| LangSmith Studio | 执行可观测性参考，非直接业务竞品 | Thread、Trace、Run | 单次任务的多次模型/工具调用可以追溯 | 将完整调试器、内部状态树全塞进聊天 |

### Taskade：工作与 Agent 的关系清楚

**公开事实：**工作空间容纳项目、成员、Agent 和自动化；多 Agent 团队可以选择协作模式，通过连接项目共享知识。官方教程描述了对任务使用 Agent、从任务位置查看其对话的路径。[工作空间](https://www.taskade.com/wiki/taskade/workspace)、[多 Agent 教程](https://www.taskade.com/learn/agents/multi-agents)。

**判断：**它值得借鉴的是“工作在哪里发生”，不只是几个 Agent 连续说话。对本项目，普通讨论仍留在群聊；当有人要求编码、测试、整理文档时，应能生成或关联一个明确任务，之后在原处查看结果。

**边界：**官方教程不足以证明所有模式可靠，也不证明它替我们实现了代码版本交接。不能把连接同一项目等同于任意私有文件都可互读。

### Linear：任务、责任和委托有独立语义

**公开事实：**Issue 是基本工作单元；委托给 Agent 时可保留人类负责人，分配与委托历史进入任务活动记录。[概念](https://linear.app/docs/conceptual-model)、[分配与委托](https://linear.app/docs/assigning-issues)。

**判断：**这是本项目最应该补的“系统性”：谁负责、Agent 做哪一部分、目前什么状态、交付的哪个版本，不能靠翻聊天猜。人类负责人不等于每一步必须人工批准；可配置自动验收。

**视觉观察：**官方局部示例把状态、负责人、标签放在属性区域，正文与属性分开。这支持“内容主区＋按需属性区”的方向；该示例不是完整应用截图，不据此规定精确尺寸、颜色或所有页面行为。

### Teams：会议不是只有消息流

**公开事实：**Facilitator 提供会议中的协作笔记、议程辅助与问答，会后可从 Recap/Notes 回看成果。微软资料区分了正式能力与预览能力；Planner 任务集成在所查管理文档中标为预览，不按普遍可用能力计算。[会议使用说明](https://support.microsoft.com/en-us/teams/copilot/facilitator-in-microsoft-teams-meetings)、[部署与限制](https://learn.microsoft.com/MicrosoftTeams/facilitator-teams)。

**判断：**本项目的会议需要“讨论、决策、待执行事项、交付物”的清楚出口；不能让用户从大量系统消息中重建会议结果。需要人类补充时应给出明确问题、处理入口和权限提示。

**边界：**会议助手不等于通用多人多 Agent 编码平台，不借此声称微软已有与我们相同的闭环。

### Dify：设置、运行和反馈分别有位置

**公开事实：**供应商配置、模型及默认模型有明确入口；应用日志区分对话和工作流运行，可查看输入输出、状态、耗时及执行详情。知识库有独立检索测试入口。[模型供应商](https://docs.dify.ai/en/cloud/use-dify/workspace/model-providers)、[日志](https://docs.dify.ai/en/cloud/use-dify/monitor/logs)、[检索测试](https://docs.dify.ai/en/cloud/use-dify/knowledge/test-retrieval)。

**判断：**我们不应让一个供应商表单同时混合凭据管理、135 个模型的浏览、默认策略、测试日志和故障诊断。需要形成稳定分区与统一反馈规则；API Ping、流式测试和 Agent 实际任务成功属于不同验证级别。

**边界：**本项目已有供应商配置、测试入口及知识检索验证，不是从零补一遍。应统一模型选择与配置归属，并补可靠性证据。Dify 的工作流生产日志也不能等同于本项目多 Agent 实际协作成功。

### OpenHands：编码产物要落在执行环境里

**公开事实：**当前文档区分 Agent Canvas、执行后端、工作区和模型访问；Canvas 组织会话、文件、终端及配置。文档还明确区分当前 Canvas 与旧 Local GUI，不能拿旧截图代表当前产品。[Canvas 概览](https://docs.openhands.dev/openhands/usage/agent-canvas/overview)。

**判断：**编码交付应由具体文件版本、修改、测试输出构成。测试 Agent 要拿到被交付的同一版本，不能靠用户复制代码串联两个私有工作区。建议设计受控的任务产物交接，不擅自开放全部个人目录。

**边界：**本项目当前有个人工作区、沙箱工具和工作记录；缺的是普通用户能稳定完成交接的路径。本次未安装或运行 OpenHands，不给其执行成功率背书。

### LangSmith：详细过程属于可展开的追踪

**公开事实：**模型调用、工具调用等可作为 Run，单次操作组合为 Trace，多轮操作归入 Thread；Studio 区分详细 Graph 模式与较简化的 Chat 模式。[可观测性概念](https://docs.langchain.com/langsmith/observability-concepts)、[Studio](https://docs.langchain.com/langsmith/studio)。

**判断：**本项目可以保留小型可交互消息摘要，再打开具体执行详情。详情应关联来源消息、执行尝试、工具结果与交付版本；无需把几百条后台扫描记录放在对话主线，也不能伪称记录了模型隐藏思维。

## 对本项目的诊断

| 维度 | 已有能力 | 仍需解决的问题 | 本地证据 |
| --- | --- | --- | --- |
| 多人协作 | 邀请成员、会话访问控制、实时消息、@ | 双人真实同时操作尚未在优惠案例中验收 | 多人验收样例及成员邀请记录 |
| 多 Agent | 定向任务、主动发言限制、有话想说提示、队列 | 任务责任、执行尝试与最终交付没有统一工作对象 | runtime、inbox、orchestrator；此前用户反馈 |
| 任务 | 团队待办、完成状态 | 当前待办载荷主要是文本和 done，不能承担执行依赖、版本与验收 | `plugins/ai-todo/index.ts` |
| 可观测性 | 原消息关联、工具工作记录、最近处理、全队队列 | 缺少统一的“一个任务的全部尝试与最终结果”视角 | workspace overview / runtime worklog |
| 资料 | 知识库、私有记忆、引用来源 | 用户仍需理解记忆、召回、索引与文件边界；跨会话记忆效果未完整验收 | RAG、知识库页面、多人样例边界 |
| 编码交付 | 文件写入、沙箱执行、个人工作区 | 私有隔离下缺少产品化交接；实际协作曾卡在模型请求失败 | 多人协作试验：超时、fetch failed |
| 视觉结构 | 共享组件、令牌、局部公共操作区 | 页面类型与交互规则没有全产品一致落实 | UI 评审及连续截图反馈 |
| 验收 | 类型/回归门禁、模型 Ping、流式测试 | 工程测试通过不证明用户闭环成立；需要真实产品场景验收 | 优惠案例未完成编码→测试→反馈 |

判断：底层并非一无所有；当前更像一组已有能力的管理页面，距离能交付结果的协作产品还有一段。继续添加孤立入口会扩大理解成本。

## 推荐采取的顺序

1. 先确定主场景、对象关系和状态含义，冻结新页面与临时组件；阻塞性故障照常修。
2. 为会话、任务详情、资源浏览和设置四类页面画完整状态原型；沿用现有组件与令牌，不换技术栈追求新鲜感。
3. 优先让“需求→编码产物→独立测试→修复→验收→后续记忆”一条路径真实完成，记录失败恢复。
4. 再根据这条路径扩展其他场景；品牌、配色和排版规范与上述原型一起落地，不当作最后刷漆。

具体范围、暂不做事项及逐项验收见 [产品方向](direction.md)。
